# 09 自动发布方案规划

## 一、定位

09 当前已经完成的核心职责是：

- 收集可上架素材
- 统一出版元数据
- 生成平台专属上架包
- 在 Web 界面中浏览、编辑、检查这些结果

因此，下一步不应该把 `09-publish.ps1` 改造成一个“既生产元数据又直接乱点网页”的超长脚本，而应该新增一层：

`09 上架包生成` + `09 自动提交器`

也就是说：

- `09-publish.ps1` 继续负责生成标准化上架包
- 新的自动化模块只负责“登录后台、填写表单、上传文件、保存草稿、等待人工确认”

这样才能保护当前 09 已有能力不退化。

---

## 二、目标边界

### 第一阶段目标

第一阶段建议只做到“半自动发布”：

1. 自动打开目标平台后台
2. 自动进入目标提交页面
3. 自动填写核心元数据
4. 自动上传 EPUB / 封面 / 附件
5. 自动保存草稿或停留在最终确认页
6. 不自动点击最终发布按钮

### 暂不纳入第一阶段

- 自动最终提交
- 自动定价
- 自动税务与收款设置
- 自动 DRM 策略决策
- 自动处理验证码 / MFA / 风控拦截
- 自动处理平台政策弹窗的所有分支

---

## 三、平台策略

### 1. Amazon KDP

适合第一批接入浏览器自动化。

建议能力：

- 登录后进入 Bookshelf
- 新建 ebook 或更新既有草稿
- 填写标题、副标题、作者、描述、关键词、分类
- 上传 `book.epub`
- 上传 `cover.png`
- 保存草稿
- 截图留档

风险：

- 页面结构变动频繁
- 可能出现验证码或额外验证
- 某些字段有区域性差异

结论：

可以做“辅助发布机器人”，不建议第一版做全自动最终提交。

### 2. Google Play Books

也适合第一批接入浏览器自动化。

建议能力：

- 进入 Partner Center
- 选择新书或更新已有书籍
- 填写书籍信息、简介、关键词、分类
- 上传 EPUB / PDF / 封面
- 保存草稿
- 截图留档

风险：

- 后台表单步骤多
- 不同账号权限下界面可能略有不同

结论：

可以作为与 Amazon 并行的第二个浏览器自动化平台。

### 3. Apple Books

不建议第一阶段走浏览器自动化。

建议路线：

- 保留 `09d-apple.ps1` 继续生成 Apple 交付包
- 第二阶段再单独研究交付工具链
- 不和 Amazon / Google 的浏览器自动化混成同一实现

原因：

- Apple Books 更接近交付工具流程，而不是普通网页后台操作
- 当前 Windows 本地环境不适合作为 Apple 自动投递的首选落点

结论：

Apple 先做“标准化交付包”，后做“专属投递器”。

## 四、推荐模块结构

建议在 `engine/` 下新增：

```text
09f-submit.ps1
09g-amazon-bot.ps1
09h-google-bot.ps1
09i-apple-delivery.ps1
```

### 1. `09f-submit.ps1`

总控提交器。

职责：

- 接收 `BookName / Language / Platform / Mode`
- 检查 09 上架包是否存在
- 选择对应平台提交器
- 统一记录日志、截图目录、执行结果
- 回写自动发布状态

不负责：

- 不直接控制浏览器细节
- 不直接填写平台字段

### 2. `09g-amazon-bot.ps1`

Amazon KDP 提交器。

职责：

- 启动浏览器自动化
- 读取 `09_publish/<lang>/amazon/` 下的上架包
- 登录后填写 Amazon 表单
- 上传文件
- 保存草稿
- 输出截图与执行报告

### 3. `09h-google-bot.ps1`

Google Play Books 提交器。

职责与 Amazon 类似，但完全使用 Google 的页面定位规则。

### 4. `09i-apple-delivery.ps1`

Apple 专属投递器预留模块。

第一阶段可先只输出：

- 当前 Apple 包是否完整
- 后续投递建议
- 工具链准备状态

## 五、浏览器自动化技术建议

建议优先使用：

- `Playwright`

不建议第一阶段使用：

- 纯 PowerShell 控 UI
- 自己拼接浏览器 DOM 操作脚本

原因：

- Playwright 更稳定
- 文件上传能力成熟
- 页面等待、元素定位、截图、失败重试都更适合这种系统

### 建议目录

```text
engine/
  automation/
    package.json
    playwright.config.js
    submit-amazon.js
    submit-google.js
    common/
      session.js
      logger.js
      upload.js
      screenshot.js
      metadata-map.js
```

说明：

- PowerShell 继续做总控
- Node + Playwright 负责浏览器层
- 两层之间通过 JSON 文件和命令参数通信

## 六、输入输出设计

### 输入来源

自动提交器应只依赖当前已经生成好的 09 上架包，不直接回头读 01/02/03。

主输入为：

- `09_publish/<language>/publish_metadata.json`
- `09_publish/<language>/publish_manifest.json`
- `09_publish/<language>/<platform>/metadata.json`
- `09_publish/<language>/<platform>/*.txt / *.md / *.json`
- 对应的 `epub / pdf / cover`

### 输出建议

每次自动提交都应写到：

```text
09_publish/<language>/submit_runs/<timestamp>/
```

里面建议包含：

- `submit_request.json`
- `submit_result.json`
- `session.log`
- `screenshots/step-01.png`
- `screenshots/step-02.png`
- `screenshots/error-final.png`

如果成功保存草稿，还应记录：

- 平台草稿号
- 平台页面 URL
- 最后停留步骤

---

## 七、执行模式

建议定义三种模式：

### 1. `prepare`

只检查上架包是否齐全，不启动浏览器。

### 2. `draft`

自动填写并上传，保存草稿，但不发布。

### 3. `assist`

自动填到最后一步，然后停住，等待人工点最终确认。

第一阶段只做：

- `prepare`
- `draft`
- `assist`

不做：

- `publish`

---

## 八、字段分级

自动化里不能把所有字段都当成同一风险级别。

### A 类：适合自动填

- 标题
- 副标题
- 作者
- 简介
- 关键词
- 分类建议
- 语言
- 封面
- EPUB / PDF 文件

### B 类：适合自动带出，但建议人工确认

- Publisher
- Imprint
- Rights
- Territory
- Distribution rights
- Series 信息
- 目标读者分级

### C 类：第一阶段不自动提交

- 定价
- 税务
- 收款
- DRM
- 最终发布日期
- 是否立即上架

---

## 九、日志与可观察性

自动发布模块必须比普通脚本更强调可观察性。

每次运行至少要记录：

1. 使用了哪个 BookName
2. 使用了哪种语言
3. 使用了哪个平台
4. 本次提交模式
5. 上传了哪些文件
6. 页面执行到哪一步
7. 是否保存为草稿
8. 是否遇到验证码 / MFA / 权限拦截
9. 最终停留页面截图

Web 界面可以后续新增：

- 自动发布运行记录
- 最近一次提交截图
- 平台草稿状态
- 最后停留步骤

---

## 十、Web 界面接入建议

建议在现有 `09 上架中心` 基础上再增加一块：

### 1. 新增区域

`09 自动提交`

### 2. 建议控件

- 平台选择
- 语言选择
- 模式选择：`prepare / draft / assist`
- 是否复用登录会话
- 运行自动提交
- 打开提交截图目录

### 3. 结果展示

- 当前状态：未开始 / 运行中 / 需人工确认 / 已保存草稿 / 失败
- 最后一步
- 平台草稿链接
- 最近截图
- 原始执行日志

---

## 十一、最小落地顺序

建议按下面顺序做，不要一口气上三平台。

### 第一步

做 `09f-submit.ps1`

先只负责：

- 参数接收
- 平台路由
- 日志目录
- 调用外部自动化脚本

### 第二步

做 `09g-amazon-bot.ps1`

先只做到：

- 读取 Amazon 上架包
- 打开后台
- 登录后进入目标页
- 自动上传文件
- 自动填写基础字段
- 保存草稿

### 第三步

做 Web 界面的“自动提交”入口

### 第四步

再做 `09h-google-bot.ps1`

### 第五步

最后再单独规划 `09i-apple-delivery.ps1`

---

## 十二、最终定义

可以把 09 自动发布模块定义为：

> **09 自动发布模块是 SageWrite 上架中心的第二层能力。第一层负责生成统一出版元数据与平台上架包，第二层负责基于这些标准化结果，使用浏览器自动化或平台专属交付链完成半自动提交流程，并将过程日志、截图与草稿状态回写到本地工作台。**

---

## 十三、当前建议结论

当前最稳的落地方案是：

1. 不改坏现有 `09-publish.ps1`
2. 新增 `09f-submit.ps1` 作为自动提交总控
3. 第一平台先做 `Amazon`
4. 第一版只做到“自动填写 + 自动上传 + 保存草稿 / 停在确认页”
5. `Apple` 暂不走浏览器自动化

这个方案改动最小、风险最可控，也最符合 SageWrite 现在“先把中间文件与观察能力做清楚，再自动执行”的整体风格。
